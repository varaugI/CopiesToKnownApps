# ADR 001: Architecture Decision Record — ConnectChat Platform

## Status
Accepted

## Context
The prototype application (`CopiesToKnownApps/WhatsApp`) is currently a pure client-side React application with simulated state stored in `localStorage` and mock data. To transform it into a scalable, production-ready, learning-grade realtime communication platform named **ConnectChat**, key architectural decisions must be made across frontend, backend, database, realtime delivery, calling infrastructure, media storage, local storage, security, and progressive infrastructure expansion.

## Decisions

### 1. Frontend Architecture
* **Framework**: React 19 with Vite, TypeScript, and React Router.
* **State Management**:
  * Server State: **TanStack Query** for fetching, caching, and synchronizing asynchronous server state.
  * Realtime & Call State: **Zustand** only for narrowly-scoped transient state (active call, mic/camera controls, socket connection state, typing indicators, active composer).
  * Persistent Local Store & Outbound Queue: **IndexedDB** (`idb` wrapper) for caching offline messages, conversation summaries, and queuing outbound messages during network disconnections.
* **Form & Validation**: **React Hook Form** + **Zod** for schema-validated DTOs and forms.
* **Testing**: **Vitest**, **React Testing Library**, and **Playwright** (for multi-context end-to-end browser flows).

### 2. Backend Architecture
* **Pattern**: **Stateless Modular Monolith** under `WhatsApp/backend`.
* **Framework**: **NestJS** with **Fastify** adapter for high-performance non-blocking HTTP and WebSocket handling.
* **Modules**: Identity, Accounts, Verification, Devices, Sessions, Contacts, Privacy, Conversations, Group Membership, Communities, Messages, Receipts, Reactions, Search, Attachments, Voice Notes, Status, Channels, Presence, Typing, Notifications, Calling, Signaling, Moderation, Audit, Observability.
* **Layering**: Strictly separated Gateway/Controller -> DTO & Zod/Class Validation -> Authorization Policy -> Application Service -> Domain Logic -> Persistence Repository -> Outbox Event Producer -> Response Mappers.

### 3. Data Layer & Persistence
* **Source of Truth**: **PostgreSQL** with **Prisma ORM** for migrations, relational integrity, and schema safety.
* **Indexes**: Explicit B-tree and GIN indexes for normalized account lookups, direct-conversation uniqueness, group membership, message sequence numbers, unread device receipts, and Channel updates.
* **Caching & Ephemeral State**: **Redis** for socket connection mapping, rate limiting, presence, typing expiry, call session locks, hot conversation metadata, and BullMQ job queues.

### 4. Realtime Messaging & Transport
* **Protocol**: **Socket.IO** with **Redis Adapter** for horizontal backend scalability.
* **Guarantees**: At-least-once delivery with client-assigned `clientMessageId` and sender device ID for server-side idempotency.
* **Delivery States**: `PENDING_LOCAL` -> `SENDING` -> `ACCEPTED` (durably stored on server) -> `SENT` -> `DELIVERED` (acknowledged by recipient device) -> `READ` (acknowledged when chat opened).
* **Reliable Publication**: Transactional **Outbox pattern** via PostgreSQL to avoid dropped messages during WebSocket publisher blips.

### 5. Media & Attachment Storage
* **Storage Engine**: **MinIO** (S3-compatible object storage).
* **Upload Flow**: Signed pre-signed S3 upload URLs generated by backend after authorization. Direct browser-to-MinIO upload. Background processing with **BullMQ** for thumbnail generation, image optimization, and audio waveform metadata extraction.

### 6. Calling Infrastructure
* **Media Protocol**: Browser **WebRTC** peer connections (`RTCPeerConnection`).
* **Signaling**: WebSocket (Socket.IO) signaling server on NestJS backend.
* **ICE Infrastructure**: **STUN** and **coturn** TURN server for NAT traversal. Short-lived TURN credentials generated per call session.

### 7. Security, Privacy & End-to-End Encryption Strategy
* **Phase 0-14**: Transport security (TLS/HTTPS/WSS). False claims of end-to-end encryption are explicitly removed.
* **Phase 15**: Client-side **Signal-Protocol-compatible** end-to-end encryption integration using reviewed libraries. Key management, identity keys, prekey replenishment, and client-side encryption/decryption.

### 8. Progressive Infrastructure Expansion
* **Deferred Systems**: Redpanda/Kafka (event streaming), OpenSearch (advanced message search), ScyllaDB/Cassandra (wide-column message store), and Kubernetes deployments are deferred to later evaluation phases (Phases 18–23) after empirical benchmarks justify their introduction.

## Consequences
* Simple operational footprint during early phases with containerized Docker Compose dependencies (Postgres, Redis, MinIO, Coturn).
* Clear module boundaries prevent microservice sprawl while enabling future service extraction if measurements demand it.
* Guaranteed data consistency and strict idempotency for messaging.
